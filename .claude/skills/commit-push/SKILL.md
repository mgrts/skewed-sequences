# Commit & push for skewed-sequences

Analyze pending changes, review them, run the test suite + pre-commit hooks, update
docs if needed, **bump the package version**, write a Conventional Commits message, and
push to `main`. Optionally push a release tag.

The default branch is **`main`**; origin is **`git@github.com:mgrts/skewed-sequences.git`**
(GitHub, owner `mgrts`). This is a solo research repo, so the default flow pushes
directly to `main` after gates pass and the user confirms.

## Arguments

`$ARGUMENTS` — optional. A free-form commit message (used verbatim as the subject after
type inference) and/or flags: `--no-push` (commit only), `--minor` / `--major` (bump
level instead of the default patch), `--release` (also create and push a `v<version>`
tag). There is **no issue tracker** — never invent ticket references.

## Important

- **Every commit bumps the version** (user decision, 2026-09-12): patch by default
  (`1.2.3 → 1.2.4`), `--minor` / `--major` on request. The bump is part of the commit,
  never a separate one. Tags are still opt-in via `--release`.
- **Conventional Commits**: `type(scope): subject`. Types: `feat`, `fix`, `refactor`,
  `perf`, `test`, `docs`, `chore`, `build`, `ci`. Scope is optional but encouraged
  (e.g. `loss`, `models`, `train`, `data`, `cli`, `config`, `experiments`, `viz`, `claude`).
- **NEVER** list Claude among commit authors. Do not add a co-author trailer naming
  Claude or Anthropic, set the author to Claude/Anthropic, use an Anthropic e-mail
  address, or add a "generated by" line naming Claude — to the commit message OR a PR
  body. This is a hard project rule, not a default: the `guard_git` PreToolUse hook
  **blocks** any commit carrying such attribution, so a slip is denied rather than
  committed. (The same hook screens the whole shell command text, so never paste
  example attribution lines into a heredoc that also contains a commit command.)
- **Never `git add -A` / `git add -u` / `git add .`.** `references/` is deliberately
  untracked (it holds the reviewed article DOCX, the JupyterHub `mlruns.db`, sweep logs
  and analysis CSVs — user decision 2026-09-12), and the `block_large_secret` hook
  treats those flags as "scan the whole working tree", so it refuses the command on the
  gitignored artifacts under `references/` anyway. Stage by explicit path (Step 9).
- Do **NOT** use `--force`, `--no-verify`, or any destructive git flag. The repo's
  guard-git hook will block these anyway. If a step fails, stop and ask the user.

## Flow

### Step 1: Gather changes

```bash
git status --short
git diff --staged --stat
git diff --stat
git branch --show-current
```

If there are no changes, stop: "Nothing to commit." If the current branch is not `main`,
note it and ask the user whether to proceed on this branch or switch. Note which
untracked paths are outside `skewed_sequences/`, `tests/`, `scripts/`, `.claude/` and
the top-level docs/config files — those need an explicit decision (default: leave
`references/` untracked).

### Step 2: Run the code-review skill

Invoke the `code-review` skill on the pending diff.

- **Critical / High** findings: stop. Show them and ask whether to proceed anyway, fix
  automatically, or cancel. Do not move on without explicit acknowledgement.
- **Medium / Low** findings: print as a heads-up and continue.

### Step 3: Run tests

```bash
make test        # poetry run pytest  (242 tests as of 2026-09-12; read the live count)
```

If tests fail: show failures, try to fix obvious causes from the diff (e.g. an
import-path drift after a rename, or a pinned count in `test_config.py` that needs to
move with a config change), re-run. If still failing, stop and ask.

### Step 4: Run pre-commit hooks

```bash
make pre-commit    # poetry run pre-commit run --all-files
```

If hooks fail: black/isort/flake8/end-of-file/trailing-whitespace auto-fix on a re-run —
re-run once. If they still fail after one auto-fix pass, stop and ask. Never bypass with
`--no-verify`. If `check-added-large-files` or `detect-private-key` trips, do NOT try to
force it through — surface the offending file to the user.

### Step 5: Update documentation

Read `README.md` and `CLAUDE.md`; update only sections that drifted from reality:

- **New CLI command / sub-app** → README CLI reference table + `CLAUDE.md` package map.
- **New `config.py` constant or changed default** → README Configuration table.
- **New module under `skewed_sequences/`** → `CLAUDE.md` package map (+ README structure).
- **Test count changed** → README "N tests" claim and `CLAUDE.md` (the count is read from
  `pytest --collect-only -q`).
- **A CRITICAL invariant changed** (lazy imports, OUTPUT_LENGTH, MLflow keys, loss
  convention, resume contract) → update the relevant `CLAUDE.md` section.
- **Claude Code setup changed** (skills/agents/hooks) → the "Claude Code setup" section
  of `CLAUDE.md`, and the pinned counts / file lists inside `.claude/skills/*` and
  `.claude/agents/*` if they reference something that moved.

If nothing drifted, skip this step. Do not rewrite docs that are already correct.

### Step 6: Bump the version (every commit)

```bash
poetry version            # current, e.g. skewed-sequences 1.2.3
poetry version patch      # or: poetry version minor | major  (per --minor / --major)
poetry version            # new
```

`poetry version` edits `version` under **`[tool.poetry]`** in `pyproject.toml` — never
add a PEP 621 `[project]` table (the Dockerfile's `poetry build -f wheel` depends on the
poetry table). Record `old -> new` for the commit body. If `--release` was passed, the
tag `v<new>` is created in Step 10 after the push.

### Step 7: Generate the Conventional Commits message

**Subject** (≤ 72 chars): `type(scope): summary`. Infer the type from the diff:

- new capability (loss, dataset, model, CLI command) → `feat`
- bug fix → `fix`
- behaviour-preserving restructure → `refactor`
- speed/memory → `perf`
- tests only → `test`
- docs/CLAUDE.md/skills only → `docs`
- tooling/deps → `chore` / `build`

If `$ARGUMENTS` supplied a message, use it verbatim as the subject (after the type).

**Body** (after a blank line): one line per significant change. If config grids, MLflow
keys, model shapes, resume-match keys, or experiment naming changed, explicitly note the
synchronized test/consumer updates so the contract reads as kept-whole. Always end with
the version line:

```
Version: 1.2.3 -> 1.2.4
```

No AI-attribution trailer.

### Step 8: Show summary and confirm

Print: code-review result, test result, pre-commit result, doc updates (or "none"),
version bump (`old -> new`), the exact paths to be staged, and the full commit message.
Then ask with `AskUserQuestion`:

```
question: "Commit and push to origin/main?"
header: "Commit & Push"
options:
  - "Yes" — stage the listed paths, commit, rebase onto origin/main, push.
  - "Commit only (no push)" — commit locally, leave the push to the user.
  - "No"  — cancel, leave the working tree as-is.
```

Do NOT proceed without an explicit "Yes" / "Commit only".

### Step 9: Commit and push

Write the message to a file **in a separate tool call** (the guard hook screens the
whole shell command, and the message may legitimately mention hooks or attribution
rules), then stage **by explicit path** — the tracked files that changed plus the new
files under the source/test/script/setup directories, plus `pyproject.toml` for the bump:

```bash
git add pyproject.toml CLAUDE.md README.md scripts skewed_sequences tests .claude
git status --short | grep '^??'        # must list nothing but references/ (or paths the user chose to leave out)
git commit -F <message-file>
git fetch origin main
git rebase origin/main
```

Only add other top-level files (`Makefile`, `Dockerfile`, `poetry.lock`, `.gitignore`,
…) when they actually changed — list them explicitly. If the rebase conflicts,
**abort** (`git rebase --abort`) and tell the user to resolve manually — do not
auto-resolve. Then (unless `--no-push`):

```bash
git push origin main
```

If the push fails (branch protection, auth, network), do NOT retry and do NOT force.
Show the error and suggest pushing a feature branch + opening a PR
(`git switch -c <branch> && git push -u origin <branch> && gh pr create`).

### Step 10: Optional release tag (only with `--release`)

Read `version` from `pyproject.toml` (`poetry version -s`), form `v<version>`. Check it
does not already exist:

```bash
git rev-parse "v<version>" 2>/dev/null
```

If it exists, surface that and skip. Otherwise confirm with `AskUserQuestion`, then:

```bash
git tag -a "v<version>" -m "Release v<version>"
git push origin "v<version>"
```

If the tag push fails, do NOT retry or delete the local tag; report that it exists
locally and can be pushed manually.

### Step 11: Final report

```
Pushed to origin/main (<short sha>).
Review: passed (or: N findings)   Tests: N passed   Pre-commit: passed
Doc updates: <files or "none">
Version: <old> -> <new>            Tag: <v.. pushed | skipped>
```

Or, if the push was blocked, show the error and the feature-branch + PR suggestion.
